Assignment 2 — Scope Delta Analysis

Dropped

  • Synchronous, blocking call to the printer vendor's REST API — the kiosk no longer waits on an HTTP response before doing anything else.
  • The old "success response → show Checked In" shortcut. There's now a real intermediate state (pending) the UI has to render honestly.

Modified

  • Duplicate-scan protection: it now has to hold across the pending window, and survive webhook confirmations arriving out of order relative to when badges were scanned. Implemented via a per-attendee active_job_id — a webhook only advances the state it was issued for.
  • The attendee state machine grew from a two-state model (not-checked-in / checked-in) to not_checked_in → pending → checked_in, plus print_failed as a recovery branch.

Added

  • A real webhook endpoint (POST /api/pivot/webhook/print-complete) that didn't exist before — the kiosk now exposes something to the outside world instead of only calling out.
  • Idempotency handling for webhook retries, and staleness handling for a job superseded by a later scan.
  • A print_failed recovery path — not explicitly required by the brief, but without it a failed print leaves an attendee stuck in pending forever. Flagged here as an addition beyond the literal spec, not left silent.

Regression check

All original acceptance behaviors still hold under the new model: at least 3 attendees supported, a result shown on screen, and a duplicate scan of an already-in-progress or already-checked-in attendee never produces a second print job. Verified directly against the running Day 4 server (duplicate scan while pending → 409, duplicate after check-in → 409, replayed webhook → no-op the second time, unknown/stale job → safely ignored).

Obsolete code

The pre-pivot synchronous flow is not running alongside the live kiosk — it's isolated in its own module (/api/original/*) and its own page (/day3), explicitly labeled deprecated, kept only so this comparison has something real to point at.
